| # | 課題 |
|---|---|
| 1 | デバイスを設置したあとにファームウェアを更新するのが大変 |

## 2. 全体の考え方

台帳を 2 つ用意し、課題をどちらかにひも付ける。

- **デバイス台帳**（git で管理する YAML）: MAC、名前、回路のリビジョン、ファームウェアの版、設置場所、電池の閾値を持たせる。課題 1・5・6・8 をここにひも付ける。
- **栽培の記録**（LINE から入力し、クラウドに保存して自宅に取り込む）: 作付け、記録、課題、写真を持たせる。課題 2・3・4 をここにひも付ける。
- 課題 7 で遅いのは、コードを書く部分ではなく実機での確認。エージェントが実機検証（HIL）を自分で回せるようにする。

## 3. 調査で分かったこと

### 3.1 電池と欠測

- 本番の機体は、どれも電池電圧を測っていない。
  - Unit Cam の `VOLT` はソーラーパネルの電圧（GPIO0 の分圧を ADC2 で読む試作）。サーバーの「8% 未満なら長く眠らせる」判定は、実際には「日が当たっていないか」を見ている。
  - S3 温度センサーは固定値 `VOLT:100` を送っている。
- **Unit Cam が止まったままになる原因（ほぼ確定）:** GPIO0 は起動モードを決めるピン（ストラッピングピン）。電池切れのあとに GPIO0 が LOW のまま電源が入ると、書き込みモードで待ち続ける。これまで、止まったら電源の入れ直しが必要だった。Deep Sleep からの復帰では判定がやり直されないので、毎回は起きない。
- 眠っている間の電流（INA226 の実測、[ina226_mode_comparison.md](../../devices/m5stack_unit_cam/dist/ina226_mode_comparison.md)）: OV2640 は約 23mA、OV3660 で待機モード `full` だと約 1.7mA。本番機はすでに OV3660。
- Unit Cam で外に出ているピンのうち、ADC に使えるのは GPIO0 だけ。HY2.0-4P の G16/G17 は ADC に使えない。
- S3 Sense は、電池電圧を測るピンの記載がコード（GPIO4）、README（GPIO6）、回路図の PNG（GPIO2）で食い違っている。

### 3.2 ファームウェアの更新

- どの機体もパーティションが factory だけで、OTA 用の領域がない。
- 送信先の MAC や計測間隔はビルド時に埋め込まれている。ドングルも、設定ファイルにある MAC しか送信先として登録しない。
- Unit Cam には自動で書き込みモードに入る回路がなく、書き込みには USB-TTL が要る。
- アプリの大きさ（2026-11-21 に `espflash save-image` で測定）:

| 機体 | フラッシュ | アプリ |
|---|---|---|
| Unit Cam | 4MB | 1.08MB |
| XIAO ESP32-C6 | 4MB | 1.04MB |
| XIAO ESP32-S3（温度センサー） | 8MB | 1.00MB（今の 1MB の領域の 95%） |

## 4. 課題ごとの方針

### 4.1 ファームウェアの更新（課題 1）: OTA を最優先にする

書き込みが必要になる場面を 3 つに分けて減らす。

| 変えたいもの | 方法 |
|---|---|
| 送信先の MAC・計測間隔・閾値・補正値 | NVS に保存する。サーバーからの指示で変えられるようにする |
| ドングルへの機体の追加 | 送信するときに、送信先を自動で登録する |
| ファームウェア本体 | Wi-Fi の OTA。2 面に交互に書き、失敗したら前の版に戻す |

流れ:

1. デバイス台帳に、機体ごとに入れるべき版を書く（stg と prod で別々に）。
2. 機体は送信のたびに `FW:` で今の版を報告する。台帳と違えば、サーバーの返信に「更新あり」と SHA-256 を載せる。
3. 機体はそのときだけ Wi-Fi につなぎ、ThinkPad の LAN 側（ファイアウォールで LAN からだけ受け付ける）から新しい版を取る。
4. 自己診断（センサーの読み取り、ドングルとの往復、OTA サーバーへの到達）に通ったら、その版を正常とする。それまでは Deep Sleep に入らない。

安全策:

- ESP-IDF の標準の仕組みで、書き込み中の電源断では壊れない。
  - 新しい版は、動いていない側の領域に書く。
  - 起動する側の情報（otadata）は、2 つのセクターに番号付きで書く。
  - 書き終えたら、イメージが正しいかを検証する。
  - ロールバックを有効にすると、自己診断に通る前にリセットされた場合は前の版に戻る。
- 電池のチェックは、無駄な試行を防ぐために入れる。

| 安全策 | 内容 |
|---|---|
| 始める条件 | 電池電圧が閾値（例: 3.8V）以上。電池を測れない機体は日中（例: 10〜14 時）に限る |
| 失敗したとき | 前の版に戻ったことを報告する。その版の再試行は翌日以降。3 回失敗したら通知する |
| 機体の取り違えの防止 | イメージに入っているプロジェクト名と版を確かめる。SHA-256 が一致したときだけ切り替える |
| 次の更新ができない版を出さない | HIL で毎回、次の 2 点を確かめる。新しい版からさらに次の版へ更新できること。壊した版を入れたら前の版に戻ること |
| 書き換えないもの | ブートローダーとパーティション表 |
| Wi-Fi | 機器用の SSID とパスワードは変えない |

- パーティション: 4MB の機体は factory を置かず、2 面を約 1.9MB ずつ取る（ESP-IDF 標準の表は 1 面 1MB なので収まらない）。
- 前提: ベランダで 2.4GHz の Wi-Fi が届くこと（段階 0 で測る）。
- 各機体とも、USB での書き込みが最後に 1 回だけ必要。

### 4.2 電池（課題 5）

- Unit Cam は Timer Camera に置き換える（4.3）。
- C6 は分圧回路がある設計なので、OTA の試験と合わせて電池電圧の報告とアラートを作る。
- S3 温度センサーには、最後の USB 書き込みのときに分圧回路を足す。
- HASH に `VBAT:<mV>`、`SOLAR:<mV>`、`RST:<リセット理由>`、`FW:<版>` を追加する。`VOLT:` の意味を機体ごとに変えない。
- 保護は ％ ではなく mV で判定する。下限に近づいたら、機体の側で動作を止める。
- サーバー側: Grafana の Unit Cam の「電圧」を「ソーラー電圧」と表示し直す。日中の発電が何日も低いままなら通知する。

分圧回路の作り方:

- 同じ値の抵抗 2 本で電池電圧を半分にする（4.2V → 2.1V）。
- 抵抗は大きめにする（220kΩ×2 なら約 0.01mA。10kΩ×2 だと約 0.2mA 流れ続ける）。
- ADC のピンと GND の間に 0.1µF のコンデンサを入れる。
- ADC1 のピンを使う。ストラッピングピンは避ける。
- 補正値はテスターで実測して決め、NVS に保存する。

### 4.3 カメラの置き換え

M5Stack Timer Camera（U082、OV3660、技適 211-200921）に置き換える。2026-11-21 に 2 個購入した。

- 内蔵の RTC（BM8563）が、基板全体の電源を切って決めた時刻に入れ直す。公称の待機電流は 2µA。
- ESP32 とカメラのピン配置が Unit Cam と同じなので、今のファームウェアの大半を流用できる。
- 電池電圧を測る回路が付いている（G38、ADC1）。電源の保持は G33。
- USB-C で書き込める。8MB の PSRAM がある。
- **注意: 電源ごと切れるのは電池で動いているときだけ。** USB や Grove の 5V から給電すると切れない（Deep Sleep で約 18mA の報告あり）。そのため、ソーラー充電（パネル → SD05CRMA → 14500）を電池の入力（SH1.0 のコネクタか VBAT のパッド）につなぐ。内蔵の電池は使わず、並列にもしない。
- 見積もり: 日中だけ 10 分ごとに撮ると、1 日あたり約 26mAh。
- 届いたら評価する: 眠っている間の電流、動作する電池電圧の下限、画質。
- 置き換えたあと、Unit Cam は HIL 用にする。

見送った案:

- Unit Cam への後付け: 空いているピンが足りず、Timer Camera の電源回路を作り直すことになる。
- XIAO ESP32S3 Sense ＋ TPL5110: 間隔が抵抗で決まる固定値になる。3.5V で起動しにくい問題も残る。
- FireBeetle 2 ESP32-S3: 待機電流の実測情報がない。

### 4.4 回路設計の管理（課題 6）

- KiCad の回路図を正とし、git・CI・レビューで管理する。
- 置き場所: 機体ごとに `devices/<name>/hardware/` に置き、シンボルとフットプリントは共通の `hardware/lib/` にまとめる。
- 既存の ASCII 図と PNG は、KiCad で描き直す。
- 電源、DS18B20、電池の計測などは、使い回せる部品として用意する。
- リビジョンを回路図と git のタグに付け、デバイス台帳の `hw_rev` と対応させる。
- CI で `kicad-cli` を動かし、ERC、PDF、部品表を出す。
- `.agents/skills/` を `.claude/skills/` にリンクし、KiCad 用のスキルを使えるようにする。
- 回路レビューのチェックリストを作る。最初の項目は「起動モードに関わるピンにつなぐ回路は、リセットの瞬間の電圧を確かめる」と「回路図のピンとファームウェアのピン定義が一致しているか」。

### 4.5 部品管理（課題 8）

- Part-DB を M1 Max（OrbStack）で動かす。
- 収納の箱や袋ごとに写真を撮り、LLM に読み取らせて一括で登録する。箱には番号のラベルを貼る。
- 破損した部品の扱い:

| 状態 | Part-DB での扱い | 現物 |
|---|---|---|
| 破損が確定 | 理由をコメントに書いて引き落とす | 廃棄するか、破損品の箱に入れる |
| 破損の疑い | 保管場所を「要確認」に移す | ラベルを貼った別の箱に分ける |

- `ENFORCE_CHANGE_COMMENTS_FOR=part_stock_operation` を設定し、在庫を動かすたびに理由の入力を必須にする。
- 破損の経緯は `hardware/lessons/NNN-slug.md` に 1 件 1 ファイルで残す。front matter には日付、型番、機体、リビジョン、原因の分類を書く。再発防止策は回路レビューのチェックリストに足す。
- Part-DB の MCP サーバーを使い、Claude Code から在庫の操作とナレッジの記録をまとめて行う。書き込みの権限は絞って有効にする。

### 4.6 栽培の記録とスマホの写真（課題 3・4）

- 入口は LINE 公式アカウントにする（外部への提供を見据えて）。
- 受け口は GCP に置き、face_reader の構成を流用する。自宅サーバーは公開しない。

```
LINE → Cloud Functions（署名の検証、Pub/Sub へ）→ Cloud Run（Gemini で整理・返信、Firestore と Cloud Storage に保存）
                                                          │
自宅サーバー ← Pub/Sub から取りに行く（外向きの通信だけ）←──┘
```

- 整理には Gemini（`gemini-3.5-flash-lite`、EU）を 1 回呼ぶ。応答トークンの期限（1 分）に間に合うので、記録のやり取りは無料の返信で済む。費用は 1 件 1 円未満の見込み。
- こちらから送る通知（プッシュ）は、無料プランで月 200 通まで。栽培の通知だけを LINE で送り、機器のアラートは Slack に残す。
- 自分用の段階では、自分の LINE ユーザー ID 以外は受け付けない。LIFF SDK は v2.31.2 以上に固定する。
- 画面は LINE ミニアプリで作る（LIFF はミニアプリに統合される予定）。外部に提供する段階では、画面とデータをクラウドに置く。
- 課題は「発見 → 対処 → 経過観察 → 解決」を 1 件として追跡し、散布のリマインドを出す。
- 最初に確かめること: LINE で送った写真の解像度と撮影日時がどこまで残るか。
- 栽培日誌の基本設計（docs/1_CultivationDiary）は長期の構想として残し、まず自分用の最小版を作る。

### 4.7 データの活用（課題 2）

判断したいことから逆算して、1 つずつ作る。

| 順番 | 判断したいこと | 出すもの |
|---|---|---|
| 1 | 機体が止まりそうか | アラート（4.2） |
| 2 | ハダニが増えやすい状況か、次の散布はいつか | 高温・乾燥が続いたときの通知、散布のリマインド、効果の確認 |
| 3 | いつ収穫できるか | 開花の記録と積算温度（開花後およそ 1,000℃）からの予測 |
| 4 | 生育に異変がないか | 1 日 1 枚の代表画像に、ローカルの VLM で説明文を付ける。タイムラプス |
| 5 | 次のシーズンに何を変えるか | 振り返りをまとめ、ナレッジを更新する PR にする |

- 害虫の判定に VLM は頼らず、スマホの接写を使う。
- 画像の保持: デバイスの画像は 1 年間すべて残す。それ以降は、代表画像と記録にひも付いた画像だけ残す。画像は別にバックアップする。

### 4.8 開発サイクル（課題 7）

- HIL: M1 Max に検証用の機体、3 台目のドングル、INA226 をつなぐ。`just` のレシピで、書き込み、数サイクルの動作確認、消費電力の測定を行う。ドングルの MAC には書き込めないようにする。
- 機体ごとの CLAUDE.md に、手順とはまった点を書く。
- HIL のスクリプトは、合否と失敗箇所の抜粋だけを返す。全ログはファイルに出す。

LLM の使い分け（Claude は Pro プランの枠で使う）:

| 用途 | 使うもの |
|---|---|
| 開発（実装・設計・レビュー） | Claude Code ＋ Opus 5.5 |
| 長い試行の繰り返し、決まった形の修正 | Sonnet 5.5 |
| 検索やログの仕分けをするサブエージェント | Haiku 5.5 |
| PR の自動レビュー | GitHub Actions ＋ `claude setup-token` |
| 定期のまとめ（週ごとの記録、シーズンの振り返り） | M1 Max で `claude -p` |
| LINE での記録の整理 | Gemini（GCP、従量課金） |
| 画像の説明文、ログの要約、埋め込み | ローカル LLM（M1 Max） |

- Fable 5.2 は Pro では利用クレジット（従量課金）になる。まず Opus 5.5 で OTA の設計レビューを行い、見落としの数と重さを見てから使うかを決める。
- 自動実行（`-p`）では、モデルを明示する。

## 6. 決定事項（2026-11-21）

- OTA を最優先にする。
- スマホからの記録は LINE 公式アカウントで受け付け、画面はミニアプリで作る。受け口は GCP（face_reader の構成を流用）。整理には Gemini を使う。
- Part-DB は M1 Max に置く。
- 栽培日誌の基本設計は長期の構想として残し、まず自分用の最小版を作る。
- Unit Cam は Timer Camera（U082）に置き換える。2 個購入済み。
- Fable 5.2 を使うかは、Opus 5.5 の結果を見てから決める。
